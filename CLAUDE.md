# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

WeighPoint admin frontend: weighing reports plus reference data (vehicles, landfills, carriers, waste types, users). React 19 + TypeScript + Vite, React Router 7 (data router), TanStack Query 5. UI text and code comments are in Russian; keep it that way.

## Commands

```sh
cp .env.example .env    # VITE_API_URL — API origin; requests go to `${VITE_API_URL}/api/v1`
npm run dev             # Vite dev server
npm run build           # tsc -b + vite build
npm run typecheck       # tsc -b only
npm run lint            # oxlint (config: .oxlintrc.json)
npm run format          # prettier --write src  (format:check to verify)
docker compose up -d --build   # nginx on :8080 (FRONTEND_PORT); VITE_API_URL is a build arg
```

There is no test suite. Verify changes with `typecheck`, `lint`, `format:check` and `build`.

## Architecture

`src/app` wires the router and QueryClient, `src/features/<entity>` holds one folder per entity, `src/shared` holds the HTTP client, hooks and generic UI, and `src/widgets/layout/AppLayout.tsx` is the sidebar shell. The sidebar's right edge and its grip resize it (`useSidebarResize`): it snaps to full (240px) or collapsed (88px, icons with small captions, vertical theme switch), a click on the grip toggles it, the choice is kept in localStorage (`wp.sidebar.collapsed`), and the width is the `--sidebar-w` variable on `.layout`. On narrow screens the sidebar stays on top and can't be collapsed. Import with the `@/` alias for `src`.

### HTTP and session (`shared/api`)
- `http.ts` is the only fetch wrapper. The server returns JSON with `text/plain`, so responses are parsed from text. Errors become `ApiError` (`status`, `code`, `fields`); server field names (`Errors.PlateNumber`) are camelCased to match form keys.
- On 401 it refreshes once (concurrent 401s share one refresh promise) and retries; if refresh fails it clears the session and `RequireAuth` redirects to `/login`.
- `session.ts` is a `useSyncExternalStore` store over `localStorage` (`wp.session`), synced across tabs. `app/queryClient.ts` clears the whole query cache on logout and never retries `ApiError`s.

### Roles and permissions (`features/auth/permissions.ts`)
- Role and own landfill are read from the JWT: role from `role` or the `http://schemas.microsoft.com/ws/2008/06/identity/claims/role` claim (lowercased), landfill from the `landfill` claim (`useOwnLandfillId`).
- `MATRIX` maps roles to permissions and mirrors the server (`RoleGroups` in the backend). Roles are cumulative: `employee` creates reports and views reports and reference data; `accountant` adds report review/editing and landfill analytics; `admin` adds full control of their own landfill (users, reference data, landfill settings, report deletion); `developer` can do everything except creating reports. Use `useCan(permission)` in components and `RequirePermission` around routes. This is visibility only — the server enforces access.
- `landfills.own` (admin) adds a «Мой полигон» item to the sidebar that opens `/landfills/<own id>`; `RequireLandfillAccess` lets a landfill page through for `landfills.view` or for the own landfill. `landfills.edit` (admin, developer) edits a landfill; `landfills.manage` (developer) creates, deletes and restores landfills. `GET /landfill/{id}` returns `employees: null` to roles without the right to see users.
- Only `developer` has `landfills.view` (the Landfills section and links to landfill pages) and `landfills.filter` (the landfill filter on Reports/Vehicles/Users). Other roles work only within their own landfill: `useLandfillFilter` hides the filter and drops `landfillId` from URL-tracked filters for them. When adding a landfill filter or a link to `/landfills/:id`, gate it the same way.
- Every reference record (carrier, vehicle make, waste type, vehicle) and every user and report belongs to one landfill, and each landfill has its own reference lists. Only `developer` has `landfills.assign`. The `LandfillField` select appears in create forms (and in user and report edit forms) only with that permission; other roles create records in their own landfill, which the server fills in. Detail pages show the landfill with `LandfillInfoRow`, which renders only for `landfills.view`.
- Reports: `reports.create` (employee, accountant, admin; not developer) creates a report from the web; `reports.edit` (accountant, admin, developer) edits reports and replaces their photos; `reports.delete` (admin, developer) deletes a report permanently. Sent reports are read-only and can't be deleted.
- Users: `users.admin` (admin, developer) changes any role, including promotion to admin. The server forbids changing your own role or blocking yourself, so the user page hides those buttons on the current account (`useMe`); `EntityActions` hides «Удалить» when `onDelete` is not passed. Users are not deleted but blocked: the user page says «Заблокировать»/«Разблокировать» (`deleteLabel`/`restoreLabel` of `EntityActions`), the API is still `DELETE` and `PATCH …/restore`.
- `analytics.view` (accountant, admin, developer): the «Аналитика» section (`features/analytics/AnalyticsPage.tsx`) shows one landfill's yearly tiles, the netto chart and the reports calendar. Others see their own landfill; a developer picks one (`landfillId` in the URL, defaults to the first landfill).
- `inactive.view` (admin, developer): list pages of landfills, carriers, vehicles, waste types and users show a «Показывать неактивные» checkbox (`InactiveToggle` in the `toolbar` slot of `ListPage`). It is stored in the URL as `inactive=true` and sends `includeInactive=true`; `useInactiveFilter` hides it and ignores the URL key for other roles. Reports have no such toggle.
- `inactive.restore` (admin, developer): detail pages of deleted (inactive) records show «Восстановить» instead of «Удалить» via the `restore` prop of `EntityActions` (`restoreAction` in `shared/lib/restoreAction.ts`).

### Feature folders
Each entity has `api.ts` (types + `xxxApi` object of `http` calls), `hooks.ts` (query key factory `xxxKeys` + `useQuery`/`useMutation` hooks), list/detail pages and a form modal.
- Query keys: `all` → `lists()`/`list(params)`, `one(id)`, and sub-keys like `analytics(id)` nested under `one(id)` so invalidating a detail also refreshes its analytics.
- Mutations invalidate the entity's keys; deletes invalidate only `lists()` (the deleted detail page is navigated away from). User/vehicle mutations also invalidate `landfillKeys.details()` because landfill pages embed users and vehicles.
- Dropdowns load reference lists page by page (50 per page, more on scroll) with server-side search via `useRemoteOptions` (`shared/lib/remoteOptions.ts`): `useLandfillOptions(value?)` / `useCarrierOptions(landfillId?, value?)` / `useMakeOptions(landfillId?)` / `useWasteTypeOptions(landfillId?, value?)` / `useVehicleOptions(landfillId?, value?)`. Spread `remoteSelectProps(options, emptyLabel)` into `Select`. Given `value`, the hook fetches the selected record's label when it is not on the loaded pages; forms may also pass `current` (e.g. a just-created record) for an instant label. The developer-only landfill filter on list pages is `LandfillFilter`. A developer sees every landfill, so forms pass the record's landfill to keep vehicle → make/carrier and report → vehicle/waste type inside one landfill, and they reset dependent selects when the landfill changes. For other roles `landfillId` stays undefined and the server scopes the lists.

### Pages and shared UI
- List pages use `ListPage` + `useListParams(filterKeys)`: page, page size, search and filters live in the URL search params. `ListPage` renders the filter bar, count, pager and skeleton rows; `renderRow` must return an element with `key`. Shared row components and column headers (`UserRow`/`USER_COLUMNS`, `VehicleRow`/`VEHICLE_COLUMNS`) are reused by embedded tables on detail pages, which render through `StaticTable` (`shared/ui/StaticTable.tsx`, shares `TableHead` with `ListPage`).
- The reports list opens a report in a side panel (`ReportDrawer`) instead of navigating: the open report is the `report` search param next to the list filters, ←/→ and the panel buttons step through the current page, Esc or a second click on the open row closes it, F expands it to the whole content area, and its left edge resizes it between 40% of the window and the sidebar (`useResizableWidth`, width kept in localStorage); releasing the edge at the sidebar expands it. The panel renders the same `ReportView` as `/reports/:id`, which stays a full page for direct links and «Открыть страницей».
- Detail pages use `DetailPage` (header, skeleton, 404/error state) with a render-prop child; page-level hooks that need data go in an inner `XxxView` component. Its not-found and error states, like the app-level 404 page (`app/NotFoundPage.tsx`, the `*` route inside `AppLayout`), use `EmptyState` (`shared/ui/EmptyState.tsx`).
- Link to entity pages with `EntityLink` (`shared/ui/EntityLink.tsx`), not `Link`: it stores the current URL (with query) in router state, so the detail page's back button and the post-delete redirect return there (`shared/lib/backNavigation.ts`, chain capped at 10 steps). `backTo` on `DetailPage`/`useDeleteFlow` is only the fallback for direct visits.
- Modals: `Modal` wraps native `<dialog>` and only mounts children while open. Forms are inner components (`XxxForm`) so their state initializes from props on each open — don't reset form state in effects. `Modal` ignores `close` events bubbled from nested dialogs; a nested modal must still be rendered outside the parent `<form>`.
- Forms use `TextField`/`Field`/`FormError`/`FormActions` from `shared/ui/Form.tsx` and keep state in `useForm(initial, mutation.error)` (`shared/lib/useForm.ts`): `set(key)`/`update(patch)` change values and clear their errors, `validate(errors)` shows local errors and returns `true` when there are none, `error(key)` shows a local validation message first, then the server field error (`fieldError`).
- Shared pieces: `CalendarMonth` (month grid of both date pickers), `PeriodSwitch` (chart period buttons), `FileButton` (upload button with a hidden file input). Small helpers: `cx` (`shared/lib/cx.ts`) for conditional class names, `clamp`/`toggled` (`shared/lib/math.ts`), `todayString` (`shared/lib/dates.ts`).
- The current account comes from `GET /auth/me` (`useMe`, `authKeys`): the sidebar shows its landfill under the logo, and `CurrentUser` (avatar, name and role) reaches `PageHeader` through `HeaderAccountContext`, so `shared` doesn't import `features`. User mutations also invalidate `authKeys.all`.
- Loading states: `Button loading` (spinner via `.btn[aria-busy]`), `Select loading`, `Skeleton*` components, and `StatCards` for analytics rows. Photos from the API render through `LoadingImage` (`shared/ui/LoadingImage.tsx`): shimmer and spinner until the image loads, then an error overlay with «Повторить»; its overlays are absolute, so the parent needs `position: relative`.
- Hover hints use `Tooltip` (`shared/ui/Tooltip.tsx`), not the native `title`: it renders into `body` with `position: fixed`, so `overflow: hidden` containers don't clip it.

### API quirks
- Paths are inconsistent: singular `/carrier`, `/landfill`, `/report`, `/vehicle-make` vs plural `/vehicles`, `/users`, `/waste-types`.
- `PUT /carrier/{id}` takes a bare JSON string body, not an object.
- Report status is `status: { code, name }`: `awaiting_sync` (photos not uploaded yet) → `awaiting_review` → `accepted` (the waste type doesn't go to ФГИС УТКО) or `awaiting_sending` → `sent` / `sending_failed`, plus `rejected` from any status before `sent` (see `features/reports/statuses.ts`); the list filters by `status=<code>`. Reviewers (`reports.review`: accountant, admin, developer) change status via `PATCH /report/status` `{ reportIds, status, comment? }` — single report on its page, bulk via row checkboxes on the list. Targets: `accepted` (the server picks `accepted` or `awaiting_sending` by waste type), `rejected` (with an optional reason, `RejectModal`), `awaiting_review` (return a rejected report), `awaiting_sending` (retry after a sending error); one-click actions are `REVIEW_ACTIONS` (`reviewActions.ts`). Allowed transitions are mirrored in `REVIEW_FROM`; the server skips ineligible reports and returns `{ updated: [{ reportId, status }], skipped: [{ reportId, reason }] }`. `GET /report/{id}/status-history` returns the history oldest first (`changedBy: null` is the system, `comment` holds the rejection reason or the ФГИС УТКО error); `ReportStatusHistory` shows it newest first under the report. `syncedAt` is when the server received the report, `sentAt` is when it was sent to ФГИС УТКО. Photo types are `photoType: { code, name }` (`vehicle`, `brutto`, `tara`). Landfill coordinates `0, 0` mean "not set" (`hasCoords`).
- Analytics: `GET /report/analytics?LandfillId=` (without `LandfillId` it covers all reports and is developer-only), `GET /landfill/{id}/analytics`, `GET /vehicles/{id}/analytics`, `GET /carrier/{id}/analytics`, `GET /waste-types/{id}/analytics`. Average fields can be `null`; show rounded kg via `formatKgRounded`. Carrier and waste type analytics include `sharePercent` — the share of the landfill's total netto, drawn with `ShareRing` (`shared/ui/ShareRing.tsx`). `GET /vehicles/{id}/analytics/netto-chart?period=week|month|quarter|year` returns `{ from, to, totalNettoKg, points: [{ from, to, value }] }` (days for a week, calendar weeks for 30/90 days, months for a year); it is drawn with the dependency-free SVG `LineChart` (`shared/ui/LineChart.tsx`, helpers in `shared/lib/chart.ts`). `GET /vehicles/{id}/analytics/visits` returns a GitHub-style yearly calendar (one report = one visit): `{ from, to, totalVisits, activeDays, maxDayVisits, days: [{ date, count }] }`, where `days` lists only days with visits and `vehiclesApi.visits` fills the rest from `from` (a Monday) to `to` (today) with zeros (`fillDays` in `shared/lib/dates.ts`); it is drawn with `ActivityCalendar` (`shared/ui/ActivityCalendar.tsx`). Landfills have the same pair: `GET /landfill/{id}/analytics/netto-chart?period=` and `GET /landfill/{id}/analytics/reports-calendar` (`{ totalReports, activeDays, maxDayReports, days }`, filled by `landfillsApi.reportsCalendar`). `GET /landfill/{id}/analytics` covers the last 12 months (`from`/`to`) and has no sent count.
- IDs of carriers, vehicle makes and waste types are GUID strings, like every other entity.
- Vehicle details return a single `landfill` (or `null`). Vehicles are no longer attached to landfills separately.
- Waste types have `requiresSending` (whether reports go to ФГИС УТКО), `licenseNumber` and `validUntil` (`YYYY-MM-DD`, also in list items). Expired licenses (`isLicenseExpired` in `features/waste-types/license.ts`) are still listed but marked in the list, on the page and in dropdowns (`Option.note`).
- Soft-deleted records are restored with `PATCH /<entity>/{id}/restore` (204). A report is deleted permanently with `DELETE /report/{id}`.
- Users: `landfillId` in create/update is sent only by a developer. The old `/users/{id}/landfills/{id}` endpoints no longer exist.
- Report create: `POST /report/web` as multipart (`vehicleId`, `wasteTypeId`, weights, `bruttoAt`/`taraAt` as ISO, plus `createdAt` as ISO — the form defaults it to now and the server rejects future dates — and required `vehiclePhoto`/`bruttoPhoto`/`taraPhoto`); it is created as `awaiting_review`. Edit: `PUT /report/{id}` with `version` from the details response. A stale version returns 409, and `useUpdateReport` then refetches the report. Editing an `accepted`/`awaiting_sending`/`sending_failed` report sends it back to `awaiting_review`. Replace a photo with `PUT /reports/{reportId}/photos/{photoId}` (plural path, `image` field); `GET /reports/{reportId}/photos` returns only the photos (used by the expanded list row). Reports carry `source` (1 mobile, 2 web), `updatedAt` and `updatedBy`. Weights, times, netto and `wasteType` can be `null` (netto stays `null` until both weights are known).

## Conventions
- Code comments describe purpose, not actions. Write «Для того чтобы React не сбросил курсор в конец, значение в DOM обновляется сразу», not «Обновляем значение в DOM» or «Делаем …». Avoid first-person verbs («делаем», «проверяем», «показываем», «сбрасываем»); use passive or impersonal forms and explain why.
- Prettier: no semicolons, single quotes, width 100, trailing commas. LF line endings (`.editorconfig`).
- Import order: `react`/`react-dom`, `react-router-dom`, `@tanstack/*`, `lucide-react`, other packages, then `@/app`, `@/features`, `@/shared`, `@/widgets`, then relative imports; the last four groups are sorted by path, case-insensitively.
- Checkboxes are styled globally (`input[type='checkbox']` in `form.css`, including `:indeterminate`); don't restyle them per component.
- Conditional classes go through `cx('base', cond && 'mod')`, not template strings; buttons use `Button` rather than raw `<button className="btn …">`; open/closed state uses `useDisclosure`.
- oxlint `react/only-export-components`: component files may export only components (and primitive constants). Put shared non-primitive constants and helpers in separate modules (e.g. `columns.ts`, `shared/lib/*`).
- Use React 19.2 `useEffectEvent` instead of disabling hook lint rules; avoid `setState` inside effects.
- Styles are plain CSS in `src/styles/*.css` imported through `styles/index.css`; design tokens are in `tokens.css`. Light and dark themes: use color tokens (`--surface`, `--bg`, `--text-*`, `--line`, `--primary-solid` for filled backgrounds under white text, etc.) instead of literal colors; dark values are overridden in `tokens.css` for `[data-theme='dark']` and for `prefers-color-scheme: dark` unless `data-theme='light'`. The choice (light/dark/system) lives in `shared/lib/theme.ts` (`wp.theme` in localStorage), is applied before first paint by the inline script in `index.html`, and is switched by `ThemeSwitch` in the sidebar. License plates stay black on white in both themes.
